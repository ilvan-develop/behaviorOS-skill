# P1.3 — Truth Governance: Design Document

**Date:** 2026-08-18
**Author:** MD Agent (automated)
**Status:** PLANNING

---

## 1. Executive Summary

P1.3 audits the existing truth enforcement mechanism to prove it correctly implements Truth Governance. The investigation answers a single question:

> "When BehaviorOS allows an agent to execute an operation requiring a specific truth level, can we prove the decision was made by the correct evidence, correct risk, correct threshold, and within the correct context?"

**Key decisions:**
- Audit-first, no duplicate truth engine
- truth-gate.json remains disabled (authority superseded)
- policy-resolver.json is the sole source of truth
- P1.3 does not block all F-phases, but HIGH/CRITICAL operations must respect existing enforcement

---

## 2. Architectural Decisions

### ADR-P1.3-001 — Truth Authority

policy-resolver.json is the sole source of truth-governance thresholds and enforcement actions.

**Rationale:** Duplicate truth engines create ambiguity about which threshold applies. Single authority ensures deterministic enforcement.

### ADR-P1.3-002 — Truth Gate Configuration

truth-gate.json remains disabled because its authority is superseded. It must not duplicate policy-resolver thresholds.

**Rationale:** Re-enabling truth-gate.json without removing policy-resolver.json would create two competing truth sources. The current kernel-based enforcement is sufficient.

### ADR-P1.3-003 — Execution Relationship

P1.3 governs the correctness of the BehaviorOS enforcement layer; it does not become a prerequisite for every product phase, but unresolved Truth Governance blockers must prevent HIGH/CRITICAL governed operations.

**Rationale:** Freezing all F-phases for a governance audit is disproportionate. LOW/MEDIUM risk operations can proceed under existing enforcement.

## 3. Current Architecture

### Truth Enforcement Flow

```
risk-engine.json
     │
     ├── operationRisk[operation] → risk level
     ├── fileRisk[file pattern] → risk level
     ├── domainRisk[domain] → risk level
     └── phaseRiskRules[phase properties] → risk + enforcement
           │
           ▼
policy-resolver.json
     │
     ├── truth-gate.minConfidenceByRisk[risk] → required confidence
     ├── knowledge-gate.minLevelByRisk[risk] → required knowledge level
     └── context7-gate.rules[operation] → context7 requirement
           │
           ▼
oage-enforce.js
     │
     ├── classifyOperation() → operation type
     ├── assessRisk() → risk level
     ├── resolvePolicies() → enforcement actions
     └── gate checks → ALLOW / DENY
```

## 4. Invariants I-41 → I-50

### Phase 0 — Contract & Invariants

| ID | Invariant | Description |
|----|-----------|-------------|
| I-41 | Truth authority is singular | policy-resolver.json is the sole source of truth-governance thresholds |
| I-42 | Truth decision uses policy-resolver | All truth enforcement decisions flow through policy-resolver.json |
| I-43 | Risk determines required confidence | Each risk level maps to a specific minimum confidence threshold |

## 5. Phase Breakdown

### Phase 1 — Truth Enforcement Audit

**Objective:** Prove that the existing kernel enforces truth gates correctly.

**Scope:**
- `policy-resolver.json` — truth-gate section
- `risk-engine.json` — risk calculation
- `oage-enforce.js` — truth gate enforcement
- `knowledge-hierarchy.json` — knowledge levels

**Tests:**
- Verify policy-resolver.json is read by oage-enforce.js
- Verify risk levels map to correct confidence thresholds
- Verify knowledge levels map to correct risk levels
- Verify truth-gate.json is not consulted

### Phase 2 — Confidence Chain

**Objective:** Prove that confidence declarations are properly recorded and validated.

**Scope:**
- `confidence_declared` audit events
- Evidence chain: session → operation → confidence → timestamp
- Session isolation

**Tests:**
- Verify confidence_declared events are recorded
- Verify confidence events contain required fields
- Verify session isolation (Session A ≠ Session B)
- Verify temporal validity

### Phase 3 — Risk-Based Thresholds

**Objective:** Prove that risk levels correctly determine required confidence.

**Scope:**
- LOW → 0% (off)
- MEDIUM → 60%
- HIGH → 80%
- CRITICAL → 95%

**Tests:**
- Verify LOW risk operations skip truth gate
- Verify MEDIUM risk requires 60% confidence
- Verify HIGH risk requires 80% confidence
- Verify CRITICAL risk requires 95% confidence
- Verify threshold boundaries

### Phase 4 — Adversarial Suite

**Objective:** Attempt to bypass truth enforcement.

**Attack vectors:**
- Agent claims 95% without evidence → DENY
- Session A confidence used for Session B → DENY
- LOW-risk evidence used for CRITICAL operation → DENY
- 60% confidence for HIGH operation (requires 80%) → DENY
- Stale/expired confidence → DENY
- Self-escalated confidence → DENY
- Missing evidence → DENY

### Phase 5 — Closure Evidence

**Objective:** Document P1.3 closure with formal evidence.

**Deliverables:**
- Invariant matrix I-41 → I-50
- Test evidence
- Authority decision
- Residual risks
