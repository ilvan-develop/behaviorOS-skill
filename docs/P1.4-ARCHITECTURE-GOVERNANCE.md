## 1. Executive Summary

P1.4 audits the existing architecture enforcement mechanism to prove it correctly implements Architecture Governance. The investigation answers a single question:

> "When BehaviorOS allows an agent to execute an operation that affects system architecture, can we prove the decision was made by the correct evidence, correct knowledge level, and within the correct boundaries?"

**Key decisions:**
- Audit-first, no duplicate architecture engine
- Reuse existing anti-patterns.json and monorepo-architecture-guardian skill
- P1.4 does not block all F-phases, but architecture changes must respect existing enforcement

---

## 2. Architectural Decisions

### ADR-P1.4-001 — Architecture Authority

anti-patterns.json (architecture category) and monorepo-architecture-guardian skill are the sole sources of architecture governance.

**Rationale:** Duplicate architecture engines create ambiguity about which rules apply. Single authority ensures deterministic enforcement.

### ADR-P1.4-002 — Architecture Enforcement Scope

Architecture enforcement applies to HIGH/CRITICAL risk operations that affect system structure. LOW/MEDIUM operations are exempt.

**Rationale:** Not every file edit requires architecture validation. Scope enforcement to operations that actually affect system boundaries.

### ADR-P1.4-003 — Execution Relationship

P1.4 governs the correctness of the BehaviorOS architecture enforcement layer; it does not become a prerequisite for every product phase, but unresolved Architecture Governance blockers must prevent HIGH/CRITICAL governed operations.

**Rationale:** Freezing all F-phases for an architecture audit is disproportionate. LOW/MEDIUM risk operations can proceed under existing enforcement.

## 4. Invariants I-51 → I-60

### Phase 0 — Contract & Invariants

| ID | Invariant | Description |
|----|-----------|-------------|
| I-51 | Architecture authority is singular | anti-patterns.json (architecture category) is the sole source of architecture governance |
| I-52 | Architecture enforcement uses anti-patterns | All architecture enforcement decisions flow through anti-patterns.json |
| I-53 | Knowledge level determines architecture authority | Level 2 (Architecture) is the second-highest priority in knowledge hierarchy |
| I-54 | Architecture changes require evidence | Agent cannot modify architecture without corresponding audit event |
| I-55 | Architecture evidence is session/context bound | Architecture evidence from Session A cannot satisfy Session B |
| I-56 | Expired/stale architecture evidence cannot authorize | Architecture evidence outside temporal window is treated as absent |
| I-57 | Insufficient architecture evidence => DENY | Architecture evidence below required threshold results in denial |
| I-58 | Lower knowledge level cannot satisfy higher requirement | Level 7 evidence cannot satisfy Level 2 requirement |
| I-59 | Architecture evidence cannot be self-escalated by agent | Agent cannot declare its own architecture authority |
| I-60 | Architecture Gate is enforced only through canonical policy path | Architecture enforcement through kernel only, not through duplicate engines |

## 5. Phase Breakdown

### Phase 1 — Architecture Enforcement Audit

**Objective:** Prove that the existing kernel enforces architecture gates correctly.

**Scope:**
- `anti-patterns.json` — architecture category
- `monorepo-architecture-guardian` skill
- `oage-enforce.js` — architecture enforcement
- `knowledge-hierarchy.json` — Level 2 (Architecture)

**Tests:**
- Verify anti-patterns.json is read by oage-enforce.js
- Verify architecture category exists and is enabled
- Verify knowledge hierarchy has Level 2 (Architecture)
- Verify monorepo-architecture-guardian skill exists

### Phase 2 — Anti-Pattern Enforcement

**Objective:** Prove that architecture anti-patterns are properly enforced.

**Scope:**
- arch-code-without-understanding (HIGH)
- arch-premature-abstraction (MEDIUM)
- arch-duplicate-component (MEDIUM)
- arch-out-of-scope-edit (HIGH)

**Tests:**
- Verify each anti-pattern has required fields
- Verify severity levels are correct
- Verify detection methods are valid
- Verify messages are clear

### Phase 3 — Monorepo Boundaries

**Objective:** Prove that monorepo architecture boundaries are enforced.

**Scope:**
- monorepo-cross-package-relative-import (MEDIUM)
- monorepo-circular-dependency (HIGH)
- Package isolation rules
- Import conventions

**Tests:**
- Verify monorepo anti-patterns exist
- Verify package isolation rules
- Verify import conventions
- Verify dependency graph validation

### Phase 4 — Adversarial Suite

**Objective:** Attempt to bypass architecture enforcement.

**Attack vectors:**
- Agent claims architecture authority without evidence → DENY
- Session A architecture evidence used for Session B → DENY
- LOW-risk evidence used for HIGH architecture operation → DENY
- Stale/expired architecture evidence → DENY
- Self-escalated architecture evidence → DENY
- Missing architecture evidence → DENY

### Phase 5 — Closure Evidence

**Objective:** Document P1.4 closure with formal evidence.

**Deliverables:**
- Invariant matrix I-51 → I-60
- Test evidence
- Authority decision
- Residual risks
