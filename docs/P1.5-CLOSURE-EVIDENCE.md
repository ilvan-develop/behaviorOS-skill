## 11. Addendum — 2026-08-18: Reconciliation

A 360 audit of this repo, run the same day this report was written, found that this document
contradicts itself and does not describe the enforcement that exists today. Recorded here
rather than silently rewritten, per this project's own audit-trail convention.

### 11.1 The contradiction

Section 3 marks I-62 → I-65 (version-pinning, tool-gate, permissions-matrix, version-registry)
"✅ PROVEN", with evidence "fail-closed, consumer declared" — i.e. `enforcement-completeness.test.js`
only asserted that governance-contract.json's JSON *says* these things, never that a violating
call is actually rejected. Section 8, in the same document, lists the same four policies under
"UNTESTED_POLICY... no adversarial tests proving block fires" — directly contradicting the
"PROVEN" verdict three sections earlier for the same invariants. The design document
(P1.5-ENFORCEMENT-COMPLETENESS.md) had specified "Adversarial test fires this block" as the
verification method for exactly these four invariants; the closure evidence shipped without it
and closed the phase anyway.

### 11.2 What has actually closed the gap

Three commits landed the same day, after this closure report: `tests/version-pinning-adversarial.test.js`,
`tests/permissions-matrix-adversarial.test.js` and `tests/tool-gate-adversarial.test.js` now drive
the real enforcement path (the kernel hook for version-pinning/version-registry, the real
`permission-guard.ps1`/`tool-guard.ps1` subprocesses for the other two) and assert the block
fires. `governance-contract.json` already listed them as `adversarialTests` before this
addendum; this document did not. **I-62 → I-65 are now genuinely proven**, on the evidence
those tests provide — not on the evidence Section 3 originally cited.

### 11.3 A second gap the same audit found, not previously tracked anywhere

`tool-gate.json` was declared "kernel, runtime, fail-closed" with `oage-enforce.js` as a
consumer, but the kernel only ever consumed the `git-commit` rule (audit-only, by design — see
§note on the policy). The `deny`/`ask` rules (`destructive`, `git-push`, `prisma-schema`) and
`globalRules.forbiddenPatterns` had exactly one real consumer, `scripts/guards/tool-guard.ps1`,
which nothing calls automatically — `INSTRUCTIONS.md` §16 tells agents the opposite ("o plugin
faz isso automaticamente"). This was declared enforced and adversarially tested (the PS1 guard,
in isolation, correctly blocks), while the path an agent's tool call actually takes let every
one of those rules through. Fixed the same day: `oage-enforce.js` now applies `rules[]` and
`globalRules` directly in `tool.execute.before` (see `applyToolGateRules`), and
`tests/tool-gate-adversarial.test.js` gained a kernel-level describe block proving it.

A related gap, lower severity: `scripts/run-pipeline.ps1` read `permissions-matrix.json` and
`skill-gate.json` at the top of every phase but only logged what it found — it never compared
against who was actually running the phase, so `requiredApprovals` was declared and displayed
but never enforced at the one place that runs a whole phase end to end. Fixed the same day:
`run-pipeline.ps1` now calls `permission-guard.ps1` and aborts the phase if it blocks.
`skill-gate.json` enforcement at this phase-level entry point remains a tracked gap — the guard
is shaped per-file (`-File`), and a phase has no single file to check it against; per-write
enforcement already exists via `enforce.ps1` → `skill-guard.ps1`.

### 11.4 A third, unrelated defect: this closure's own test evidence was unverifiable

`tests/enforcement-completeness.test.js` — the file this report cites as proof for I-61 → I-70 —
resolved its project root from a hardcoded absolute path (`C:\Users\Ilvan\Desktop\behaviorOS`)
instead of `dirname(fileURLToPath(import.meta.url))`, the pattern every other test file in this
repo uses. On any machine other than the one it was written on — including the `ubuntu-latest`
runner `.github/workflows/oage-ci.yml` uses for the `npm test` step — every test in that file
would fail at the first assertion (`governance-contract.json must exist`), because that path
does not exist there. The "480/480 tests passing" evidence in Section 6 was therefore never
actually validated in the CI environment this report claims to trust; it could only ever have
been run successfully on the original author's own machine. Fixed the same day (dynamic path).
